Kademlia Join Tests

Three questions about joining, answered on real laptops: what if a node starts with no bootstrap address, what if two nodes do, and what if two nodes share an ID.

The expected output on this page is real, recorded in the simulated lab (scripts/netns/). Each case is also an automated test in internal/kademlia/bootstrap_test.go: TestFirstNodeWithoutBootstrap, TestNodesWithoutBootstrapStaySeparate and TestDuplicateIDNewestSenderWins.

The flags these tests use

Each test starts with a table saying which laptop gets which flags.

FlagWhat it doesIn these tests
--port 9000UDP port for the network, and the same number on TCP for filesevery node; each laptop has its own ports
--id-seed NAMEThe node's ID is SHA-1 of this name, so the same name always gives the same ID. Leave it out for a random ID.laptopA → ebb80ed4…, laptopB → 6cde3376…, and twin → be605983… on two laptops in test 3, on purpose
--bootstrap IP:9000An existing node to join through. Leave it out and the node starts a new network of its own.left out in tests 1 and 2 for the nodes being tested
--advertise-ip IPThe address other laptops use to download files from this node. A node started without --bootstrap has nothing to detect it from, so it must be given; a joining node detects its own.every node started without --bootstrap

Before you start

All laptops on the same network: campus Wi-Fi worked for us, and a phone hotspot is the fallback.

  1. Each laptop finds its IP: the number after src. Put them in the boxes above.

    all laptopsterminal
    ip route get 1.1.1.1

  2. Build the program, plus a copy to send to B and C (about 9 MB). Run from the repo folder.

    Aterminal
    go build -o lab/node ./cmd/node && cp lab/node lab/node-linux

  3. Make the received file runnable.

    B + Cterminal
    chmod +x node-linux

  4. If sudo ufw status says Status: active on a laptop, open port 9000 there:

    all laptopsterminal, only if active
    sudo ufw allow 9000/udp && sudo ufw allow 9000/tcp

The tests

Test 1 · two laptops

What if no --bootstrap is given?

The node isn't broken: it becomes the first node of a new network, a network of one. It works alone, and the next node joins through it.

AlaptopAnone: the node under test{A}
BlaptopB{A}:9000, joining laternone: detected

    Aterminal

Test 2 · two laptops

What if two nodes both start without --bootstrap?

Two separate networks, even on the same Wi-Fi. With no tracker and no broadcast, nothing introduces them. One message does.

Laptop--id-seed--bootstrap--advertise-ip
AlaptopAnone{A}
BlaptopBnone{B}

  1. Stop every node. Both start alone:

    Aterminal
    ./lab/node --port 9000 --id-seed laptopA --advertise-ip {A}
    Bterminal
    ./node-linux --port 9000 --id-seed laptopB --advertise-ip {B}

  2. Each stores a message; each stays local (stored on 0 other node(s), locally=true):

    Anode console
    put fromA hello from A
    Bnode console
    put fromB hello from B

  3. Neither can see the other's message. Each lookup asks nobody, because each network has one member:

    Anode console
    get fromB
    Expect on A
    get fromB: 0 value(s) via network: rounds=0 rpcs_sent=0 rpcs_failed=0
    Bnode console
    get fromA
    Expect on B
    get fromA: 0 value(s) via network: rounds=0 rpcs_sent=0 rpcs_failed=0

  4. Introduce them with a single message. Every node records whoever messages it, so one PING puts each laptop in the other's table:

    Anode console
    ping {B}:9000
    Expect on A
    PONG from {B}:9000 in …

  5. Now each finds the other's message:

    Anode console
    get fromB
    Expect on A
    get fromB: 1 value(s) via network: rounds=1 rpcs_sent=1 rpcs_failed=0
    "hello from B"
    Bnode console
    get fromA
    Expect on B
    get fromA: 1 value(s) via network: rounds=1 rpcs_sent=1 rpcs_failed=0
    "hello from A"
Pass when

Before the ping, both gets find 0 values with rpcs_sent=0; after it, each finds the other's message.

Why a ping instead of a restart with --bootstrap?

Restarting B would wipe its message, since values live in memory. A ping merges the two networks with nothing lost. A full join (PING plus a lookup of your own ID, as --bootstrap does) also fills the routing table with everyone else; with two nodes, there is no one else.

Test 3 · three laptops

What if my twin joins through someone else?

Two laptops with the same --id-seed get the same ID. Nothing detects it: both join fine, and A keeps one contact for that ID, pointing at whichever twin spoke last.

Laptop--id-seed--bootstrap--advertise-ip
AlaptopAnone: the node both twins join through{A}
Btwin (same as C, on purpose){A}:9000none: detected
Ctwin (same as B, on purpose){A}:9000none: detected

  1. Stop every node. A starts; then B, then C, join through it with the same seed:

    Aterminal
    ./lab/node --port 9000 --id-seed laptopA --advertise-ip {A}
    Bterminal
    ./node-linux --port 9000 --id-seed twin --bootstrap {A}:9000
    Cterminal
    ./node-linux --port 9000 --id-seed twin --bootstrap {A}:9000
    Expect on B and on C: no error
    msg="bootstrap complete" routing_table_size=1 self_lookup_rounds=1 self_lookup_rpcs=1

  2. Two laptops joined, but A lists one contact: the shared ID, at C's address, because C spoke last:

    Anode console
    table
    Expect
    bucket 158 (distance in [2^158, 2^159)):
    be605983e1868ad74e02d30d299c00d827233260@{C}:9000
1 contacts in 1 non-empty buckets; holding values for 0 keys

  3. Now B speaks last. A pings B, and the same ID moves to B's address:

    Anode console
    ping {B}:9000
    Anode console
    table
    Expect
    bucket 158 (distance in [2^158, 2^159)):
    be605983e1868ad74e02d30d299c00d827233260@{B}:9000
1 contacts in 1 non-empty buckets; holding values for 0 keys
Pass when

Both twins join without an error, A's table holds a single contact for be605983…, and its address follows whichever twin spoke last.

Why it matters

Everything A sends to that ID, lookups and stored values included, reaches only one twin, and which one depends on timing. The protocol can't detect it, so the fix is a rule: never give two nodes the same --id-seed (or leave it out for a random ID). Joining through your own twin is different: it fails at once with has the same ID as this node.
