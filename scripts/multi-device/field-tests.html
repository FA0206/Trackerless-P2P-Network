Kademlia LAN Field Tests

Four tests that check what only real laptops on one Wi-Fi can show: a laptop announcing a wrong address, a laptop vanishing mid-download, downloading from two laptops at once, and a file surviving the death of the laptop that shared it.

Who runs what

Every command is tagged with the laptop that runs it, and with where you type it.

A · has the repo

Builds the program, starts first, shares the files. Runs ./lab/node from the repo folder.

B · second laptop

Gets node-linux from A and runs ./node-linux. Never needs to know its own IP.

C · third laptop

Only for tests 3 and 4. Same file as B, started the same way.

terminal means a normal shell. node console means typing into the window where a node is running: log lines scroll past, but typing still works. Stop a node with Ctrl+C. A fresh start means stopping every node and starting again: the network keeps everything in memory, so stopping wipes it.

Before you start

All laptops on the same network. Campus Wi-Fi worked for us; a phone hotspot is the fallback if a network blocks laptops from talking to each other.

  1. Find A's IP: it's the number after src. Put it in the box above.

    Aterminal
    ip route get 1.1.1.1

  2. Build the program, plus a copy to send to B and C over USB, Drive or Telegram (about 9 MB). Run from the repo folder.

    Aterminal
    go build -o lab/node ./cmd/node && cp lab/node lab/node-linux

  3. Make the received file runnable.

    B + Cterminal
    chmod +x node-linux

  4. Check the firewall on every laptop. If it says Status: active, open port 9000 for UDP (the network) and TCP (file data).

    all laptopsterminal
    sudo ufw status
    all laptopsterminal, only if active
    sudo ufw allow 9000/udp && sudo ufw allow 9000/tcp

  5. Make a 2 MiB test file: 32 pieces of 64 KiB.

    Aterminal
    head -c 2M /dev/urandom > lab/two-mb.bin

Standard start

Most tests begin like this. A starts first and states its IP; B joins through A and works out its own IP.

  1. Aterminal
    ./lab/node --port 9000 --id-seed laptopA --advertise-ip {A}
  2. Bterminal
    ./node-linux --port 9000 --id-seed laptopB --bootstrap {A}:9000
    Expect on B
    msg="advertise ip auto-detected" ip={B} via={A}:9000
…
msg="bootstrap complete" routing_table_size=1 …
    Expect on A
    msg="rpc received" type=PING from=…@{B}:9000 …

  3. Quick check on both: each lists exactly one contact, the other laptop, with its Wi-Fi IP.

    A + Bnode console
    table

Two laptops

Test 1

Forget --advertise-ip on purpose

A laptop started without its IP tells others "my files are at 127.0.0.1", which every laptop reads as itself. This checks the warning added for exactly that mistake.

Passed

  1. Stop both nodes. A starts without its IP; B joins as usual.

    Aterminal
    ./lab/node --port 9000 --id-seed laptopA
    Bterminal
    ./node-linux --port 9000 --id-seed laptopB --bootstrap {A}:9000
    Expect on A, the moment B joins
    level=WARN msg="advertise ip is loopback but a remote peer contacted us" advertise_ip=127.0.0.1 from=…@{B}:9000

  2. A shares the Kademlia paper; send the printed key to B over chat.

    Anode console
    share maymounkov-kademlia-lncs.pdf
    Bnode console
    fetch <key> paper.pdf
    Expect on B: it connected to itself
    msg="provider failed, trying the next one" provider=127.0.0.1:9000 error="provider refused: unknown content key …"
fetch failed: transfer: fetch manifest: every provider failed

  3. Then stop both nodes and do a standard start. B still holds the bad record, and records never expire, so restarting only A wouldn't fix it.

Pass when

A shows the warning as soon as B joins, and B's fetch fails exactly like this. Here, failing is the expected result.

Test 2

Pull the plug mid-download

On a real network, a laptop that vanishes is slower to notice than a program that quits. The download must fail cleanly, never hang.

Passed

  1. Start A so it waits 1 s before sending each piece, which gives you time to act. B joins as usual.

    Aterminal
    ./lab/node --port 9000 --id-seed laptopA --advertise-ip {A} --debug-serve-delay 1s
    Bterminal
    ./node-linux --port 9000 --id-seed laptopB --bootstrap {A}:9000
  2. Anode console
    share lab/two-mb.bin
    Bnode console
    fetch <key> two-mb.bin

  3. When B's log shows msg="piece received" … have=5, A turns its Wi-Fi off.

    Expect on B, about 25 s later
    msg="provider failed, trying the next one" provider={A}:9000 error="… i/o timeout"
fetch failed: transfer: stalled for 15s with 5 of 32 pieces: no live provider has the rest
    Bterminal
    ls two-mb.bin
    Expect
    ls: cannot access 'two-mb.bin': No such file or directory

  4. Turn Wi-Fi back on, do a fresh start, and repeat with A pressing Ctrl+C instead. B now fails after about 15 s, because A's laptop answers "nobody here" at once.

Pass when

The fetch gives up with that message in about 25 s (Wi-Fi off) or 15 s (Ctrl+C), and no half-written file is left behind.

Three laptops

C uses the same node-linux file as B, and its own firewall check.

Test 3

Two providers at once

A download pulls different pieces from several laptops in parallel.

Passed

  1. Fresh standard start for A and B, without --debug-serve-delay on either (see why below). A shares the 2 MiB file; B fetches it, which makes B a provider too.

    Anode console
    share lab/two-mb.bin
    Bnode console
    fetch <key> two-mb.bin
  2. Cterminal
    ./node-linux --port 9000 --id-seed laptopC --bootstrap {A}:9000
    Cnode console
    fetch <key> two-mb.bin
    Expect on C
    fetched "two-mb.bin" (2097152 bytes, 32 pieces) into two-mb.bin in …
    N piece(s) from {A}:9000
    M piece(s) from {B}:9000      (N + M = 32)
Pass when

C lists pieces from both A and B.

What we saw: 31 pieces from B, 1 from A, in both sharing orders.

The split follows speed, not who shared first. Each laptop gets its next piece only after answering the previous one, so a laptop that answers 30× faster gets about 30× the pieces. And once a piece is handed to a laptop, only that laptop is asked for it, so the download still waits for the slow laptop's piece at the end. A split this lopsided means one laptop answers far slower: a leftover --debug-serve-delay from test 2 or 4 is the usual cause, a weak Wi-Fi link the other. Compare ping {A}:9000 and ping {B}:9000 from C's node console to tell.

Test 4 · the headline

The seeder dies, the file survives

The project's main promise: once the downloaders together hold every piece, the laptop that shared the file can vanish, and they finish from each other.

Passed

  1. Fresh start. Every laptop sends each piece 1 s late, so there's time to act; B and C fetch one piece at a time.

    Aterminal
    ./lab/node --port 9000 --id-seed laptopA --advertise-ip {A} --debug-serve-delay 1s
    Bterminal
    ./node-linux --port 9000 --id-seed laptopB --bootstrap {A}:9000 --debug-serve-delay 1s --max-inflight 1
    Cterminal
    ./node-linux --port 9000 --id-seed laptopC --bootstrap {A}:9000 --debug-serve-delay 1s --max-inflight 1
  2. Anode console
    share lab/two-mb.bin
    Bnode console
    fetch <key> two-mb.bin

  3. When B's log shows have=10, C starts too:

    Cnode console
    fetch <key> two-mb.bin

  4. When B's log shows have= somewhere between 22 and 28, A presses Ctrl+C.

    Expect on B and on C
    fetched "two-mb.bin" (2097152 bytes, 32 pieces) into two-mb.bin in …
    … piece(s) from {A}:9000
    … piece(s) from the other laptop
    provider {A}:9000 failed and was skipped
Pass when

Both B and C finish after A is gone.

Why 22–28: B and C each get about one piece a second, and they're steered to different pieces, so together they hold all 32 once B is near 21. B alone would finish at 32. Stop A earlier and some piece may exist only on A: losing the file is then the correct outcome (B and C fail with "no live provider has the rest"), so try again and stop A later.
