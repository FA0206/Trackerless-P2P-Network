Kademlia LAN Eval Runs

The real-laptop halves of two performance graphs: how fast a swarm recovers when its seeder dies (graph 3), and how much DHT traffic a download costs next to the file itself (graph 4). Each run ends in a CSV row, plotted next to the same experiment on localhost.

Same setup as the LAN field tests: no SSH, every laptop typed at by hand. Why each graph exists and how the localhost half runs: docs/10-performance-graphs.md.

Who runs what

Every command is tagged with the laptop that runs it, and with where you type it.

A · has the repo

Builds the program, shares the files, and is the seeder. Runs ./lab/node from the repo folder and appends the CSV rows.

B · second laptop

A leecher. Gets node-linux from A and runs ./node-linux.

C · third laptop

The second leecher, test 1 only. Same file as B.

terminal means a normal shell. node console means typing into the window where a node is running: log lines scroll past, but typing still works. Every node's output is also saved by tee, so the numbers can be read off afterwards. Stop a node with Ctrl+C. A fresh start means stopping every node and starting again: the network keeps everything in memory, so stopping wipes it. Every trial is a fresh start.

Before you start

All laptops on the same network. Campus Wi-Fi worked for the field tests; a phone hotspot is the fallback. No clock needs to match another: every number is read from one laptop's own log.

  1. Find A's IP: it's the number after src. Put it in the box above.

    Aterminal
    ip route get 1.1.1.1

  2. Build from this branch: graph 4 needs the bytes= field it adds to "rpc received" log lines. Then send lab/node-linux to B and C over USB, Drive or Telegram.

    Aterminal
    git checkout eval/performance-graphs && go build -o lab/node ./cmd/node && cp lab/node lab/node-linux

  3. Make the received file runnable.

    B + Cterminal
    chmod +x node-linux

  4. Check the firewall on every laptop. If it says Status: active, open port 9000 for UDP (the network) and TCP (file data).

    all laptopsterminal
    sudo ufw status
    all laptopsterminal, only if active
    sudo ufw allow 9000/udp && sudo ufw allow 9000/tcp

  5. Make the test files: 4 MiB for test 1 (64 pieces of 64 KiB — bigger than the field tests' 2 MiB file, so there's room for a kill point that clearly loses the file, one right at the edge, and one that clearly survives), and the four sizes for test 2.

    Aterminal
    head -c 4M /dev/urandom > lab/four-mb.bin && for s in 64K 1M 10M 100M; do head -c $s /dev/urandom > lab/f-$s.bin; done

Test 1 · 9 runs

Kill the seeder at 40%, 60% and 80%

Does the file survive its seeder, and how long until every leecher is receiving pieces again? 3 trials at each kill point. Every node sends each piece 1 s late, so there's time to act; B and C fetch one piece at a time, as in field test 4. These kill points aren't an arbitrary 25/50/75 split: with this file size and stagger, B and C's pieces naturally cover the whole file by the time B itself is ~60% done (measured by running with no kill at all and watching where the union first reaches 64/64) — so 40% reliably loses the file, 60% sits right at that boundary, and 80% reliably survives it, a deliberate spread instead of three points landing on the same side.

  1. Fresh start, saving every log.

    Aterminal
    ./lab/node --port 9000 --id-seed laptopA --advertise-ip {A} --debug-serve-delay 1s 2>&1 | tee a.log
    Bterminal
    rm -f four-mb.bin; ./node-linux --port 9000 --id-seed laptopB --bootstrap {A}:9000 --debug-serve-delay 1s --max-inflight 1 2>&1 | tee b.log
    Cterminal
    rm -f four-mb.bin; ./node-linux --port 9000 --id-seed laptopC --bootstrap {A}:9000 --debug-serve-delay 1s --max-inflight 1 2>&1 | tee c.log

  2. A shares the file; send the printed key to B and C over chat. B starts fetching.

    Anode console
    share lab/four-mb.bin
    Bnode console
    fetch <key> four-mb.bin

  3. When B's log shows have=8, C starts too.

    On B, look for
    msg="piece received" … of=64 from={A}:9000 bytes=65536 have=8 inflight=0
    Cnode console
    fetch <key> four-mb.bin

  4. When B's log shows the kill point, A presses Ctrl+C: have=26 for 40%, have=39 for 60%, have=52 for 80%.

  5. Wait until B and C both end. Either is a valid result.

    Survived
    fetched "four-mb.bin" (4194304 bytes, 64 pieces) into four-mb.bin in …
    Lost: a piece only A had (about 15 s after the kill)
    fetch failed: transfer: stalled for 15s with … of 64 pieces: no live provider has the rest

  6. On B and C: from the moment each noticed A was gone (its own provider failed line for A) to its next piece, or lost. Both times come from that laptop's own log.

    The line each one measures from
    level=WARN msg="provider failed, trying the next one" … provider={A}:9000 error="read response header: EOF"
    Bterminal
    awk -v seeder='{A}:9000' 'function ms(t){sub(/^time=/,"",t);split(t,a,"T");split(substr(a[2],1,12),h,":");return int((h[1]*3600+h[2]*60+h[3])*1000+0.5)} /msg="provider failed, trying the next one"/ && index($0, " provider=" seeder " ") && !k {k=ms($1)} /msg="piece received"/ && k && !f {f=1; r=ms($1)-k} /msg="download complete"/{ok=1; if(!k) early=1} END{if(!ok) print "lost"; else if(early) print "finished before the kill"; else printf "%d ms\n", (k && f) ? r : 0}' b.log
    Cterminal
    awk -v seeder='{A}:9000' 'function ms(t){sub(/^time=/,"",t);split(t,a,"T");split(substr(a[2],1,12),h,":");return int((h[1]*3600+h[2]*60+h[3])*1000+0.5)} /msg="provider failed, trying the next one"/ && index($0, " provider=" seeder " ") && !k {k=ms($1)} /msg="piece received"/ && k && !f {f=1; r=ms($1)-k} /msg="download complete"/{ok=1; if(!k) early=1} END{if(!ok) print "lost"; else if(early) print "finished before the kill"; else printf "%d ms\n", (k && f) ? r : 0}' c.log
    Expect on each
    1052 ms

  7. Record the trial, then do a fresh start for the next one.

    Record a graph 3 trial

    Fill in both results.

    Aterminal, repo folder
What the row means

survived is 1 when both B and C finished. recovery_s is the slower of the two, the moment the whole swarm is moving again; it's empty when the file was lost. A lost trial is a real result, not a failed run: the seeder died while some piece existed only on it.

Test 2 · 12 runs

DHT bytes vs. file bytes, four file sizes

How much DHT traffic does sharing and downloading a file cost, next to the file itself? 3 trials per size. No --debug-serve-delay here: the download runs at the network's real speed.

  1. Fresh start, saving both logs.

    Aterminal
    ./lab/node --port 9000 --id-seed laptopA --advertise-ip {A} 2>&1 | tee a.log
    Bterminal
    rm -f got.bin; ./node-linux --port 9000 --id-seed laptopB --bootstrap {A}:9000 2>&1 | tee b.log

  2. A shares the file; B fetches it.

    Anode console
    share lab/f-{S}.bin
    Bnode console
    fetch <key> got.bin
    Expect on B
    fetched "f-{S}.bin" (… bytes, … pieces) into got.bin in …

  3. Count the DHT bytes A received from its share on (its first request is the share: during B's join A only answered).

    Aterminal
    awk '/msg="rpc sent"/{on=1} on && /msg="rpc received"/{match($0,/ bytes=[0-9]+/); s+=substr($0,RSTART+7,RLENGTH-7)} END{printf "control=%d\n", s}' a.log

  4. Count the DHT bytes B received after joining, and the file bytes it downloaded.

    Bterminal
    awk 'on && /msg="rpc received"/{match($0,/ bytes=[0-9]+/); s+=substr($0,RSTART+7,RLENGTH-7)} /msg="bootstrap complete"/{on=1} /msg="download complete"/ && !p {match($0,/ bytes=[0-9]+/); p=substr($0,RSTART+7,RLENGTH-7)} END{printf "control=%d payload=%d\n", s, p}' b.log

  5. Record the trial, then do a fresh start for the next one.

    Record a graph 4 trial (size: 64K)

    Fill in both results.

    Aterminal, repo folder
What the row means

control_bytes is A's and B's DHT bytes added up: every UDP message is received exactly once, so that's all the DHT traffic of the share and the download, each message counted once. payload_bytes is the file.

Troubleshooting

What you seeWhyFix
error: bootstrap failed: …The joining laptop's packets never reach A: different networks, Wi-Fi that blocks laptops from each other, or a firewallSame phone hotspot; check sudo ufw status on A
A fetch fails mentioning 127.0.0.1 or unknown content keyA was started without --advertise-ipStop every node, then a fresh start with the commands above
Test 2's A count prints control=0The binary predates this branch: no bytes= on "rpc received" linesRebuild on eval/performance-graphs and resend node-linux
finished before the killThat laptop completed without ever noticing A was gone: Ctrl+C came too lateRedo the trial and stop A at the right have=
